# Разбор кода: Рефакторинг, инкапсуляция, чистые функции и тестирование

## Что такое рефакторинг и зачем он нужен

**Рефакторинг** — это процесс изменения внутренней структуры кода без изменения его внешнего поведения. Простыми словами, мы делаем код чище, понятнее и безопаснее, но программа при этом работает точно так же, как и раньше. 

Представь, что у тебя есть работающий механизм, но все его шестеренки разбросаны по столу и скреплены скотчем. Рефакторинг — это сборка этого механизма в аккуратный корпус. Ты не меняешь принцип его работы, но теперь в нем легко заменить деталь, не разбирая всё до основания.

**Дублирование** — это повторение одного и того же кода в разных местах программы. Это главный враг хорошего кода. Если правило или формула дублируется, то при изменении требований тебе придется искать и править каждую копию вручную. Рано или поздно ты забудешь об одной из них, и программа начнет работать непредсказуемо.

Рефакторинг обычно проводят по определенным шагам (паттернам). Ниже мы разберем основные из них на конкретных примерах.

## Шаг 1. Фиксация поведения (Защита от случайных поломок)

Прежде чем что-то менять в коде, нужно убедиться, что мы не сломаем то, что уже работает. Для этого поведение программы фиксируется с помощью тестов.

### Пример с тестированием (до рефакторинга)

```cpp
int storageFee(int hours)
{
    if (hours <= 0 || hours > 24)
        return -1;
    if (hours <= 2)
        return 100;
    return 100 + (hours - 2) * 40;
}

int checkFee(int hours, int expected)
{
    const int actual{ storageFee(hours) };
    if (actual != expected)
    {
        std::cout << "FAIL hours=" << hours
                  << " expected=" << expected
                  << " actual=" << actual << "\n";
        return 1;
    }
    return 0;
}

int main()
{
    int failed{ 0 };
    failed += checkFee(0, -1);
    failed += checkFee(1, 100);
    failed += checkFee(2, 100);
    failed += checkFee(3, 140);
    failed += checkFee(24, 980);
    failed += checkFee(25, -1);

    if (failed == 0)
        std::cout << "ALL TESTS PASSED\n";
    return failed;
}
```

Ожидаемый вывод:

```
ALL TESTS PASSED
```

Теория:
Здесь мы видим простейшее модульное тестирование. Функция `storageFee` вычисляет стоимость хранения в зависимости от количества часов. Функция `checkFee` — это тестовый сценарий: она вызывает `storageFee` с конкретным входным значением и сравнивает результат с ожидаемым. Если результаты не совпадают, выводится сообщение об ошибке, а счетчик неудач увеличивается.

В `main` мы запускаем несколько таких проверок и суммируем количество провалов в переменной `failed`. Если в конце `failed == 0`, значит, все тесты прошли.

Зачем это нужно перед рефакторингом? Если ты решишь изменить формулу или переписать функцию, эти тесты сразу покажут, не сломалось ли что-то. Это твоя страховка. Если после изменений вывод всё еще `ALL TESTS PASSED`, значит, внешнее поведение программы не изменилось, и рефакторинг прошел успешно.

## Шаг 2. Именование и типизация (Магические числа и псевдонимы)

### Проблема: Дублирование правил и магические числа

```cpp
int calculateStandardFee(int weightKg)
{
    if (weightKg < 1 || weightKg > 20)
        return -1;
    return 200 + weightKg * 30;
}

int calculateExpressFee(int weightKg)
{
    // Правило лимита скопировано вручную и позже изменилось только здесь
    if (weightKg < 1 || weightKg > 15)
        return -1;
    return 400 + weightKg * 50;
}
```

Теория:
Здесь мы видим классическую проблему: числа `1`, `20`, `15` и `-1` разбросаны по коду. Что такое `-1`? Код ошибки. Что такое `20`? Максимальный вес. Это называется магическими числами — значениями, смысл которых непонятен без контекста.
Хуже того, логика проверки веса скопирована в обе функции. Если завтра бизнес решит, что максимальный вес для стандартной доставки теперь 25 кг, придется менять число в одном месте, а в другом — не забыть. Это прямое дублирование.

### Решение: Псевдонимы типов и инкапсуляция правил

```cpp
using Kilograms = int;
using Rubles = int;

namespace parcelLimits
{
    constexpr Kilograms minWeight{ 1 };
    constexpr Kilograms maxWeight{ 20 };
    constexpr Rubles invalidFee{ -1 };
}

bool isValidWeight(Kilograms weight)
{
    return weight >= parcelLimits::minWeight
        && weight <= parcelLimits::maxWeight;
}

Rubles calculateStandardFee(Kilograms weight)
{
    if (!isValidWeight(weight))
        return parcelLimits::invalidFee;
    return 200 + weight * 30;
}

Rubles calculateExpressFee(Kilograms weight)
{
    if (!isValidWeight(weight))
        return parcelLimits::invalidFee;
    return 400 + weight * 50;
}
```

Ожидаемый вывод (для веса 18):

```
Standard: 740
Express: 1300
```

Теория:
Здесь мы исправляем предыдущую проблему с помощью двух инструментов.
Во-первых, псевдонимы типов (`using Kilograms = int;`). Это не создает новый тип, а просто дает понятное имя существующему. Теперь сигнатура функции `calculateStandardFee(Kilograms weight)` сама говорит нам, что вес измеряется в килограммах, а возвращаемое значение — в рублях.

Во-вторых, пространство имен (`namespace parcelLimits`). Мы собираем все бизнес-правила (минимальный и максимальный вес, код ошибки) в одном месте. Теперь логика проверки веса вынесена в отдельную функцию `isValidWeight`, и дублирования больше нет. Если лимит изменится, достаточно поменять одно число в `parcelLimits::maxWeight`.

## Шаг 3. Устранение скрытого состояния (Глобальные переменные и чистые функции)

### Проблема: Скрытое состояние

```cpp
int g_bonusPoints{ 100 };

int applyDiscount(int price)
{
    if (g_bonusPoints >= 100)
    {
        g_bonusPoints -= 50;
        return price - 100;
    }
    return price;
}

int main()
{
    std::cout << applyDiscount(1000) << "\n";
    std::cout << applyDiscount(1000) << "\n";
    return 0;
}
```

Ожидаемый вывод:

```
900
1000
```

Теория:
Здесь используется глобальная переменная `g_bonusPoints`. Она доступна из любой точки программы, и функция `applyDiscount` меняет её напрямую. В результате первый вызов скидывает 50 бонусов и возвращает цену со скидкой. Второй вызов видит, что бонусов осталось 50 (меньше 100), и скидку не применяет.
Это работает, но такой подход опасен: любая другая функция может случайно изменить `g_bonusPoints`, и поведение программы станет непредсказуемым. Это называется скрытым состоянием. Программа ведет себя по-разному в зависимости от того, что происходило раньше, и отследить это становится сложно.

### Решение: Чистые функции и передача параметров

```cpp
using Rubles = int;
using BonusPoints = int;

namespace loyalty
{
    constexpr BonusPoints minPointsForDiscount{ 100 };
    constexpr BonusPoints pointsSpent{ 50 };
    constexpr Rubles discountAmount{ 100 };
}

bool canApplyDiscount(BonusPoints points)
{
    return points >= loyalty::minPointsForDiscount;
}

Rubles applyDiscount(Rubles price, BonusPoints points)
{
    if (canApplyDiscount(points))
        return price - loyalty::discountAmount;
    return price;
}

BonusPoints remainingPoints(BonusPoints points)
{
    if (canApplyDiscount(points))
        return points - loyalty::pointsSpent;
    return points;
}

int main()
{
    BonusPoints points{ 100 };
    std::cout << applyDiscount(1000, points) << "\n";
    points = remainingPoints(points);
    std::cout << applyDiscount(1000, points) << "\n";
    return 0;
}
```

Ожидаемый вывод:

```
900
1000
```

Теория:
Этот вариант решает проблему глобального состояния. Теперь функция `applyDiscount` не меняет никаких внешних переменных. Она просто принимает цену и текущие бонусы, а возвращает новую цену. За списание бонусов отвечает отдельная функция `remainingPoints`.
Это называется чистыми функциями: результат зависит только от входных параметров, и нет побочных эффектов. Такой код гораздо легче тестировать, понимать и изменять. Состояние (сколько бонусов осталось) теперь явно передается через параметры, а не скрыто живет где-то в памяти.

## Шаг 4. Устранение дублирования вывода и строгая типизация

### Проблема: Строгая типизация и перепутанные аргументы

```cpp
enum class Command : int { Exit = 0, ShowStatus = 1, Start = 2, Stop = 3 };
enum class Status { Stopped, Running };

Status executeCommand(Command command, Status status)
{
    if (command == Command::Start)
        return Status::Running;
    return status;
}

int main()
{
    const Command cmd{ Command::Start };
    const Status st{ Status::Stopped };
    // Намеренная ошибка компиляции: аргументы перепутаны местами
    const Status next{ executeCommand(st, cmd) };
    std::cout << (next == Status::Running) << "\n";
    return 0;
}
```

Теория:
Здесь показана сила строгих перечислений (`enum class`). Обрати внимание на строку `executeCommand(st, cmd)`. Функция ожидает первым аргументом `Command`, а вторым — `Status`. Мы передаем наоборот. В старом C++ (с обычными `enum`) это скомпилировалось бы, потому что оба перечисления были бы просто числами. Но `enum class` создает разные типы, и компилятор сразу выдаст ошибку: «нельзя преобразовать `Status` в `Command`». Это защищает от глупых ошибок, связанных с перепутанными аргументами.

## Шаг 5. Устранение дублирования в коде (Итоговый пример)

Собирая всё вместе, давайте посмотрим на финальный результат рефакторинга из предыдущих шагов. Вместо разрозненных функций с магическими числами и глобальными переменными, мы получаем структурированный и надежный код.

Ожидаемый вывод всей программы после рефакторинга:

```
Standard: 740
Express: 1300
900
1000
ALL TESTS PASSED
```

Каждый шаг рефакторинга решает конкретную проблему:

- Фиксация поведения защищает от случайных поломок.
- Именование и типизация убирают «магические числа» и делают код самодокументируемым.
- Выделение чистых функций устраняют скрытое состояние и побочные эффекты.
- Устранение дублирования вывода (вынос общего кода в отдельные функции) и строгая типизация предотвращают логические ошибки на этапе компиляции.

В итоге мы получили код, который легко читать, легко тестировать и легко изменять, не боясь сломать что-то в другом месте.
